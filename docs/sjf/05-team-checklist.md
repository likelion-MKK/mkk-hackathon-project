# SJF Track 팀 실행 체크리스트

## 1. 문제 정의

- [ ] 세 Challenge 중 하나를 선택했다.
- [ ] “누가, 언제, 무엇 때문에 불편한가”를 한 문장으로 적었다.
- [ ] 인터뷰, 관찰, 공개 통계 등 문제 근거를 확보했다.
- [ ] 단순 현상과 해결할 문제를 구분했다.
- [ ] MCM 고객·제품·매장·헤리티지 중 핵심 자산을 하나 이상 연결했다.
- [ ] 해결책을 기능 목록이 아니라 하나의 핵심 가설로 설명할 수 있다.

## 2. AI와 데이터 설계

- [ ] AI가 실제 사용자 흐름 안에서 호출되고 결과를 반환한다.
- [ ] AI가 필요한 이유를 규칙 기반 기능과 비교해 설명할 수 있다.
- [ ] 일회성 이벤트가 아니라 반복해서 사용할 이유가 있다.
- [ ] 실제 고객 개인정보 없이 더미 데이터로 시연할 수 있다.
- [ ] 더미 데이터임을 발표와 문서에 명시한다.
- [ ] 향후 MCM API 연동 지점과 현재 독립 실행 범위를 구분했다.
- [ ] 실패, 지연, 부정확한 AI 응답에 대한 대체 흐름이 있다.

## 3. MVP 구현

- [ ] 가장 중요한 사용자 여정 하나가 처음부터 끝까지 작동한다.
- [ ] 프론트엔드, 백엔드, AI가 데모 흐름에서 실제로 연결된다.
- [ ] 핵심 기능과 무관한 부가 기능은 후순위로 뒀다.
- [ ] 모바일·데스크톱 중 주요 시연 환경에서 UI가 깨지지 않는다.
- [ ] 비밀키는 환경변수로 관리하고 GitHub에 커밋하지 않았다.
- [ ] 배포 URL을 외부 네트워크에서 테스트했다.
- [ ] 로그와 오류 화면에 개인정보나 API 키가 노출되지 않는다.

## 4. 검증

- [ ] 가설마다 성공·실패를 판단할 지표가 있다.
- [ ] 최소 3명 이상에게 핵심 흐름을 사용하게 하고 막힌 지점을 기록했다.
- [ ] “멋있다” 외에 시간 절감, 전환 장벽 감소, 재방문 의향 등 행동 지표를 확인했다.
- [ ] MCM 브랜드와 어울리지 않는 표현·시각 요소를 점검했다.
- [ ] 오래된 협업·셀럽 이미지 등 권리 불명확한 자산을 제거했다.

## 5. 제출 자료

- [ ] 프로젝트명과 한 줄 소개가 같은 메시지를 전달한다.
- [ ] 썸네일은 3:2, 권장 1200×800, 파일당 5MB 이하이다.
- [ ] 서비스 제안의 각 항목이 공백 포함 1,500자 이하이다.
- [ ] 100초 이내 MP4 데모 영상에서 핵심 흐름이 보인다.
- [ ] IR Deck은 16:9 PDF, 30MB 이하이다.
- [ ] IR 파일명이 `학교명(캠퍼스)_팀명_서비스명.pdf` 형식이다.
- [ ] FE/BE 저장소가 Public이고 제출 저장소가 3개 이하이다.
- [ ] 평가 브랜치가 `main` 또는 `master`이다.
- [ ] 제출 코드와 배포 결과가 동일하다.
- [ ] 로그인 필요 시 테스트 계정을 제공했다.

## 6. 발표·현장

- [ ] 5분 발표와 3분 질의응답을 연습했다.
- [ ] 대본을 읽지 않고 핵심 메시지를 말할 수 있다.
- [ ] 라이브 데모 3분 안에 핵심 가치가 보인다.
- [ ] 100초 최종 어필 버전을 준비했다.
- [ ] IR Deck, 데모 영상, 핵심 화면을 오프라인 저장했다.
- [ ] 부스 교대 운영표와 담당자를 정했다.
- [ ] 노트북, 충전기, 젠더, 멀티탭 보조품을 점검했다.

## 7. 제출 직전 동결

- [ ] 마감 전에 모든 파일 업로드와 재생을 확인했다.
- [ ] 최종 커밋 해시를 팀 채널에 기록했다.
- [ ] 배포 URL을 시크릿 브라우저에서 확인했다.
- [ ] 저장소와 배포 결과가 같은 버전임을 확인했다.
- [ ] 제출 후 코드·문서·배포를 수정하지 않기로 팀이 합의했다.
- [ ] 수정이 꼭 필요하면 먼저 운영진에게 공식 확인한다.
