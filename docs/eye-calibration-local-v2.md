# 시선 보정 v2 — 로컬 구현과 비교 절차

2026-09-16 사용자 승인 범위: 보정 시간 단축, 점 따라가기 UX, 표적·프레임 동기화,
품질 검사 복구, 일부 지점 보완, 로컬 비교 경로. 실제 실패 실행의 집계 진단은 확인했으며,
수정 후 성공률·시간·정확도 개선은 아직 검증하지 않았다.

## 신호가 약해도 체험을 완료하는 정책 — 2026-09-16

사용자의 후속 결정에 따라 보정 품질을 **영상 진입의 탈락 기준으로 사용하지 않는다**.
아래 변경이 이 문서의 기존 품질 실패 후 중단 설명보다 우선한다.

- Eye(양유상): 학습이 완료된 모델은 독립 검증에 실패해도 세션에 한해 추론에 사용한다.
  보정 결과 `valid=false`, 실제 실패 사유·오차·유효 비율은 그대로다. 진단의
  `inference_ready`만 별도로 표시한다. 이 모델의 유효 좌표는 `confidence=0.35`와
  `model_revision`의 `+low-confidence`로 전달한다. 0.35는 보수적인 정책 가중치이며
  실측 정확도나 확률이 아니다. 기존 상품별 evidence의 `average_confidence`까지 보존된다.
- 기본 adaptive profile은 독립 8점 확인 후 위치 오차를 이유로 추가 학습·8점 재검증을
  반복하지 않는다. 부족한 초기 학습점 보완과 fixed 비교 profile은 유지한다.
- 학습 전 얼굴 미검출·표본 부족·준비 시간 초과 등도 Kiosk(조윤혜)에서 영상으로 진행한다.
  모델이 없으면 좌표를 만들지 않고 결측 frame과 사유를 수집한다. 취소, viewport 변경,
  잘못된 프로토콜은 추론 가능한 모델로 승격하지 않는다.
- API·프롬프트(박형진·양유상)는 파생 관측 frame이 1개라도 있으면 Luna Medium을 한 번
  호출한다. 상품 AOI에 연결되지 않은 낮은 신뢰도 좌표, 표정만 있는 관측, 결측·품질 기록도
  실제 값과 사유를 보존한 B timeline으로 전달한다. 상품 영역 근거가 있으면 기존 C 또는
  source AOI B 경로를 사용한다. 프롬프트는 `central-recommender-ko-v8`이다.
- Kiosk(조윤혜)는 AI가 10개 후보를 비교해 선택한 Top 1을 그대로 표시한다. 컬렉션 첫 상품
  대체·사전 목록 조회 경로를 제거했다. 저신호 결과에는 AI 추천임을 표시하되 취향·무의식·
  특정 상품을 오래 봤다는 설명은 붙이지 않는다. 이 후속 결정이 이전 컬렉션 제안 정책을 대체한다.
- 관측 0개, API 오류, 출력 schema·상품·근거 위반, 취소는 성공으로 바꾸지 않는다.
  원본 전송·파생 frame 저장은 추가하지 않으며 취소·종료 시 모델과 관찰 버퍼를 폐기한다.
  DB schema와 공개 v2 결과 필드는 변경하지 않는다.

완료 조건: 약한 모델의 좌표·신뢰도 전달, 얼굴 미검출 후 영상 진행, 단일 관측으로 AI 호출,
모델이 고른 상품 표시, 취소 후 늦은 응답 무시, 세션 간 모델 격리. 검증은 Eye pytest, API 저신호 Luna·v2 tests,
Kiosk test/lint/build와 `python scripts/validate_contracts.py`로 수행한다.
오프라인 합성 파생 신호 검증은 실제 카메라 정확도나 Luna 호출 성공을 증명하지 않는다.

### 2026-09-16 실제 Luna 로컬 연결 확인

사용자가 파생 관측·상품 정보의 OpenAI 전송을 명시적으로 승인한 뒤 기존 키로 확인했다.
소유 경계는 API 박형진, 모델·프롬프트 양유상이며, 완료 조건은 실제 Luna 선택과 로컬 결과 조회다.

- 직접 호출: 합성 약한 시선 관측 1개, B timeline, Luna Medium/v8, 9.36초, strict 출력 검증 통과.
- 로컬 HTTP 세션: 관측 1개 ingest → complete → polling → 실제 AI Top 1 → 검수 상품 이미지
  HTTP 200까지 9.27초. 중복 complete는 같은 job을 반환했고 테스트 세션 DELETE는 204였다.
- API·Gateway·Eye·Kiosk를 실제 Luna 설정으로 다시 실행했다. 사용자 테스트 주소는
  `http://127.0.0.1:15173/`다. 카메라 테스트용 deterministic stub은 이 실행에서 사용하지 않는다.
- 로컬 실행은 검수된 v4 상품 스냅샷과 메모리 저장을 사용하며 DB 변경은 없다. `/readyz`의
  `database_not_configured` 503은 운영 DB 미연결 상태를 보존한다. 로컬 세션·추천 API는 위와 같이 동작했다.
- 호출 입력은 모두 직접 만든 합성 데이터다. 원본 웹캠 영상은 보내지 않았으며, 이번 결과는
  실제 사용자 시선 정확도나 추천 품질 검증 결과가 아니다. 다음 확인은 실제 웹캠 체험이다.

## 동작

1. ‘얼굴 맞추기 시작’ 후 같은 카메라 스트림의 좌우 반전 미리보기와 타원형 가이드를
   표시한다. Eye가 얼굴 중앙·상대 크기·양쪽 눈·고개 각도를 확인하면 초록색이 된다.
   연속 1초와 최소 15개 유효 표본을 모두 확보하면 시선 맞추기로 자동 전환한다.
   준비 표본은 학습에서 버린다. 눈이 감기거나 자세가 바뀌거나 250ms 넘게 표본이 끊기면
   안정 시간을 다시 센다. Kiosk도 600ms 넘게 진행 응답이 없으면 준비 표시를 해제한다.
2. Worker가 표적 ID·좌표를 보낸다. Kiosk는 240ms 위치 이동 및 화면 반영 후
   `performance.now()`를 기록하고, 같은 시계의 캡처 시각과 함께 frame에 붙인다.
3. Worker는 해당 session/video/표적, 단조 증가 sequence·캡처 시각만 수집한다.
   표시 후 350ms는 학습에서 제외하며, 마지막 150ms 동안 고개 안정성을 미리 확인한다.
   얼굴 미인식·깜빡임·비유효 feature는 유효 샘플로 세지 않는다.
4. 가변 방식은 유효 샘플 15개와 표본 시간 폭 500ms를 모두 확보하면 다음 점으로 이동한다.
   단, 검증·마지막 확인에서 이때 feature 유효 비율이 85% 미만이면 같은 점에서 목표를
   30개로 한 번만 늘린다. 예측 오차를 보고 수집 여부를 선택하지 않으며 이전 무효 표본도
   분모에 유지한다. 충분하면 즉시 끝나는 일반 경로는 유지하며 고정 시간 비교 모드는
   표본 목표를 늘리지 않는다.
   자세 확인은 최대 30초, 각 점은 최대 3.5초, 전체 작업은 120초 제한이다.
   2개 연속 빈 학습점 또는 4개 초과 부족 지점이면 즉시 실패하며 전체 재시도하지 않는다.
5. 부족한 학습점만 다시 수집하고 좋은 점은 유지한다. Ridge 규제 강도는 학습점 단위
   교차 검증으로 선택한다. 실제 브라우저 viewport를 학습·오차·추론에 동일하게 사용한다.
6. 학습에 쓰지 않은 8개 지점에서 원시 예측을 검사한다. 전체는 유효 비율 85% 이상,
   대각선 오차 p50 15% 이하·p95 30% 이하를 만족해야 한다. 개별 점은 유효 비율
   70% 이상, 오차 p50 25% 이하·p95 40% 이하와 최소 15개 수집 표본을 요구한다.
7. 유효 비율과 수집량을 통과하고 국소 위치 오류가 남으면 실패 영역 가까이에서 추가 학습한다.
   검출 부족은 추가 학습으로 해결할 수 없으므로 원인을 구분해 종료한다. 앞 단계 보완을 포함해 최대
   4지점이며, 오류를 보고 선택한 점을 최종 검증에 재사용하지 않는다.
   새 8개 좌표로 마지막 확인을 거친다. 최종 실패를 성공이나 중립 시선으로 바꾸지 않는다.

고개 안정성은 EyeTrax feature의 마지막 세 회전각과 0.06rad 변화 기준으로 검사한다.
작은 움직임이 누적되어도 한 지점의 기준 자세에서 벗어나면 안정화를 다시 확인한다.
학습은 해당 수집 창을 다시 시작하지만 검증은 이전 표본을 유지하고 재안정화 구간을
무효로 센다. 깜빡임만으로 고개가 움직였다고 판단하지 않고 다음 유효 frame의 자세를
기존 기준과 비교한다.
이 기준과 고정 좌표 세트는 다양한 사용자·조명에서 재검증해야 한다.

### 사용자 승인에 따른 판정 완화 (2026-09-16)

사용자의 “판정기준을 낮춰줘 너무 빡세” 요청에 따라 세 가지 브라우저 v2 profile의
공통 품질 정책을 `webcam-relaxed-v1`으로 변경했다. 소유자는 Eye 담당 양유상이다.

| 범위 | 유효 표본 비율 | 오차 중앙값 | 오차 95백분위 |
| --- | --- | --- | --- |
| 이전 전체·점별 | 90% 이상 | 10% 이하 | 25% 이하 |
| 현재 전체 | 85% 이상 | 15% 이하 | 30% 이하 |
| 현재 개별 점 | 70% 이상 | 25% 이하 | 40% 이하 |

오차의 분모는 논리 viewport 대각선이다. 완화한 전체 기준이 최종 성공 조건이고,
개별 점 기준은 일부 영역에서 신호가 거의 없거나 크게 빗나가는 경우를 걸러낸다.
기준 안의 작은 국소 흔들림만으로 추가 학습하거나 전체 실패하지 않는다. 유효 15개와
무효 2개인 구간(88.2%)도 추가 수집 없이 다음 점으로 넘어간다.

기존 무효 표본의 분모 유지, 원시 좌표 평가, 화면 밖 예측의 invalid 처리, 학습·검증 분리,
시작 전 얼굴 준비 조건과 시간 한도는 유지한다. `quality_policy_id`와 적용 임계값을
로컬 집계 진단에 포함하므로 이전 정책의 성공률과 구분할 수 있다. 이는 허용 오차 변경이며
실제 정확도 개선·상품 AOI 성능 검증이 아니다. 구형 standalone 보정 및 모델 선정용
benchmark Gate는 별도 기준으로 남긴다.

### 시작 전 얼굴 위치 안내

`face_positioning.py`의 기준은 카메라 영상 내 얼굴 중심 `(0.5, 0.5)`에서 가로 ±0.12,
세로 ±0.14, 얼굴 높이 0.32–0.78·너비 0.12–0.65다. 크기는 거리의 간접 지표이며 cm로
환산하지 않는다. 두 눈 각각의 눈꺼풀 간격·화면 안 좌표와 얼굴 축에서 계산한 각도로
준비 상태를 판단한다. 각도는 물리 측정값이 아닌 휴리스틱이며 여러 얼굴·안경·장비에서
정확도 개선을 확인한 기준이 아니다. 얼굴·눈 검출이 실제 가림을 항상 구별하지는 못한다.

고정된 EyeTrax 0.4.0 detector 호출을 관찰해 준비 정보를 얻으며 카메라나 추론기를 추가로
열지 않는다. 얼굴 가이드 자체는 시선 feature 계산과 품질 기준을 바꾸지 않는다. 준비 결과의 boolean과
`stable_ms`만 ephemeral progress에 담고, 얼굴 영상은 같은 브라우저 MediaStream의
미리보기로 표시한다. 얼굴 좌표·랜드마크는 전송·저장하지 않는다. 준비가 끝나면 미리보기를
분리하며 카메라 track은 FrameSource가 세션 수명에 맞춰 해제한다.

얼굴 가이드의 추가 범위는 시작 전 얼굴 맞춤·초록 표시·1초 후 시작이다. 보정 중 전역 자세
유지와 추정 시선 overlay는 포함하지 않는다. 품질 기준은 위의 별도 사용자 승인으로
완화했다. 얼굴 progress 추가는 Eye·Gateway 재시작이 필요하며 임계값 변경만 반영할 때는
Eye worker를 다시 시작하면 된다.

## 비교 모드

Kiosk를 실행하는 PowerShell에서 설정한 뒤 Vite를 재시작한다.

| `VITE_CALIBRATION_PROFILE` | 학습 | 확인 | 용도 |
| --- | ---: | ---: | --- |
| `adaptive-dense5-v2` (기본) | 25점 | 8점 | 화면 전체 범위를 유지하고 충분하면 조기 종료 |
| `adaptive-sparse16-v2` | 16점 | 8점 | 시간을 더 줄이는 실험 옵션 |
| `fixed-dense5-v2` | 25점 | 8점 | 같은 동기화·품질 검사에서 고정 수집과 비교 |

모든 모드는 중앙 자세 확인과 최대 4점 보완을 공유한다. 오류에 따른 보완 후에는 새
8점 확인이 추가된다. 화면의 총 단계 수가 늘 때는 ‘조금 더 모으기’로 알린다.
고정 모드는 학습 안정화 1초·검증 안정화 750ms 이후 약 1초 수집한다.
화면 반영·통신·학습 시간이 더해지므로 과거 64초 타이머와 동일한 벽시계 시간은 아니다.
16점 방식의 정확도는 아직 입증하지 않았으며 실패 시 25점 전체로 자동 전환하지 않는다.

## 로컬 화면 확인 — 카메라·API 없이

Node.js 24.19.0과 설치된 의존성을 사용해 저장소 루트에서 실행한다.

```powershell
npm run dev:kiosk -- --port 5177 --strictPort
```

`http://127.0.0.1:5177/calibration-preview.html`을 연다. 시작 전 ‘부분 보완 포함’을
선택할 수 있고, 진행 중 얼굴 미인식·깜빡임·고개 움직임을 전환하면 수집 링이 멈춘다.
표적 표시 후 캡처 표식과 단계 변경을 확인한다. 효과음은 기본 꺼짐이다.
이 화면은 짧은 합성 진행 경로이며 실제 보정 성공률·시간을 측정하지 않는다.
별도 개발용 HTML 진입점으로, production `index.html` 빌드에는 포함하지 않는다.

## 실제 카메라 비교 — 개발자 로컬 수동 실행

전체 loopback 구성은 [Demo 3-C 실행 절차](../apps/kiosk/DEMO_3C_REAL_CAMERA_SMOKE.md)를
따른다. 그 절차의 Kiosk 실행 직전에 원하는 모드를 지정한다.

```powershell
$env:VITE_CALIBRATION_PROFILE = "adaptive-dense5-v2"
npm run dev:kiosk
```

Eye·Gateway는 이번 소스로 재시작해야 새 표적 프로토콜을 처리한다. 과거 worker와 새
Kiosk를 섞으면 성공 처리하지 않는다. 배포, 외부 추천 호출, DB 변경 없이 Demo 3-C의
테스트용 추천 경로로 확인할 수 있다.

보정 직후 같은 로컬 세션이 유지되는 동안 aggregate 진단만 읽을 수 있다.

```powershell
Invoke-RestMethod http://127.0.0.1:8766/internal/eye/v1/calibration-summary
```

반환 필드: profile, `quality_policy_id`, 전체·점별 `quality_limits`, 성공 여부,
총 시간(ms), 보완점 수, 확인점 수, 유효 비율,
대각선 오차 p50/p95, 실패 사유(해당 시). 추가로 전체·유효 표본 수, 추가 수집한 점 수,
실패 항목과 점별 집계 결과를 반환한다. 무효 원인은 `blink`, `no_face`, `invalid_features`,
`stabilizing`, `invalid_prediction`, `outside_viewport`로 구분하며 세부 원인이 없는 입력은
`unavailable_features`로 센다. 비율은 동기화·적응 구간을 통과한 검증 표본 기준이며
전체 카메라 frame 전달률을 뜻하지 않는다. 세션 종료·다음 보정·worker 종료 시 폐기한다.
원본 영상·랜드마크·개별 시선 좌표와 사용자 ID는 반환하거나 저장하지 않는다.

Kiosk는 검증 표본 부족, 유효 검출 비율 부족, 위치 오차, 검출과 오차 동시 실패를
각각 안내한다. 기존 worker의 `quality_gate_failed`도 안전한 일반 안내로 처리한다.
전체 오차가 통과해도 개별 점의 오차·비율이 실패할 수 있으므로 `point_results`와
`failed_checks`를 함께 확인한다.

### 비교 판정

- 같은 사용자·카메라·조명·화면에서 모드 순서를 번갈아 여러 번 실행한다.
- 총 시간 p50/p95, 완료율, 이탈률, 보완점 수, 품질 Gate 통과율을 비교한다.
- 같은 `quality_policy_id`끼리 비교한다. 기준 완화 전후 통과율 차이를 정확도 향상으로 해석하지 않는다.
- 서로 다른 좌표 세트의 오차를 직접 순위화하지 않는다. 오류 보완 후에는 새 최종
  검증점을 사용하므로 `repair_points`가 같은 실행끼리 비교하거나 별도 공통 평가를 한다.
- 첫 25점 가변 방식의 35–45초와 16점의 20–30초는 설계 목표이며 측정 결과가 아니다.
  통신 FPS가 낮거나 재수집이 있으면 늘어난다. 같은 조건에서 정확도가 유지되는지 먼저 확인한다.
- 손·마우스 클릭으로 라벨을 추가하거나, 보정 움직임을 상품 선호·집중력 점수로 바꾸지 않는다.
- AOI hit 및 룩북 구간의 실제 유효율은 별도 평가한다. 보정 점 오차 통과만으로
  최종 상품 AOI 정확도가 검증되었다고 하지 않는다.
